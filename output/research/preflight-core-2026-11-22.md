## Findings

1. **Current worker-task authority is still on the legacy Run; migrate it next.** Original accepted assignments are immutable (`adapters/files/project-run-plans.ts:234`, `:239`) and retain original task/resource/path grants. Actual dispatch deliberately reads current `run.workerTasks` (`core/worker-envelope.ts:148`), while refinement request/save/completion mutate the Run via generic updates (`core/execution.ts:1620`, `:1649`, `:1676`). These are distinct owners today, explicitly acknowledged at `adapters/files/project-run-plans.ts:230`; this is a source-confirmed migration gap, not an observed regression. Replacing the current task with `assignment.task` would lose an accepted refinement and can revive an old compact objective after goal changes.

2. **Known failure and completion selection still require growing agent history.** `workerFailureForReplan` reads the last agent and current task (`core/worker-recovery.ts:19`), and `pendingWorkerRoles` reverses the full agent array for each role (`:82`). Dispatch writes starting/running/completed/known-failed agent state through a supplied arbitrary Run callback (`core/worker-assignments.ts:132`, `:191`, `:220`, `:272`). A narrow task command cannot prove SQL recovery by inventing a known-failure row: the actual dispatch/outcome producer or its required semantic boundary must move with the consumer. Current source verifies exact role version, original paths, envelope task and independently observed scope before allowing one refinement (`core/worker-recovery.ts:29`); preserve those conditions.

3. **Runtime observations lack durable source ownership and deduplication.** `RuntimeEvent` contains only id/Run/thread base identity (`core/runtime-events.ts:2`); `observe` scans every project snapshot, drops terminal events and deduplicates only in a lifetime in-memory Set (`core/execution.ts:2041`, `:107`). Message/command/turn projection mutates arrays and can update retained historical agents (`core/runtime-projection.ts:45`, `:64`, `:96`). The generic update attempt check (`core/execution.ts:936`) captures whichever execution owner is current when observation starts; it does not attribute an old runtime event to its original dispatch. This is a source-confirmed design gap with a stale-event attribution risk, **not an independently reproduced production stale-event failure in this review**. Thread IDs alone cannot replace session/turn ownership because coordinator resume intentionally reuses a thread (`core/execution.ts:745`). Durable journal receipts and indexed binding are a separate following slice; receipts must commit with projections and only successful commits may suppress redelivery.

4. **The complete executor still cannot run without the document aggregate.** `get` scans a snapshot (`core/execution.ts:906`), and `update` exposes Run, Goal and ProjectDocument callbacks and scans sibling Runs for autonomy (`:914`, `:929`). Continuation reads a whole snapshot for role presence (`:701`), and final acceptance still owns a generic update over evidence, commit, execution head and goal (`:1974`). Workspace/check/reviewer/session observation and result preparation remain outside the migrated scalar commands. Do not enable SQL by assembling a synthetic full Run or call the current SQL facets a migrated executor.

## Recommended coherent next slice

Introduce immutable worker-task revisions with a named current-task head linked to project/Run/current attempt/original plan/assignment. Preserve full original result contract and criteria. A focused semantic request/refine/settle boundary must compare the exact task revision, known failed assignment/session/outcome and current attempt. Requested intent consumes the existing single automatic refinement opportunity before the coordinator call. Saving the proposal may narrow inputs and focus the objective, but must not change role/resource/write paths/checks/expected result/criteria. A known result and completed release remain prerequisites to replacement; an unknown outcome never qualifies.

The request and save transactions must also reject a terminal/stopped or canceling current lifecycle, even when the attempt ID is unchanged. Across the awaited workspace inspection/coordinator call/release, compare both captured attempt and requested task/outcome revision: an attempt guard alone cannot distinguish a same-attempt stop. The present save rechecks requested status/session (`core/execution.ts:1650`) while generic update guards only attempt equality (`:943`); the new semantic owner must define the lifecycle CAS explicitly rather than treating a matching session as ongoing execution. This is a required contract for the next writer, not a claim of an independently reproduced same-attempt stop race here.

Capture current dispatch task by this head, while reading immutable role/resource/path authority from the existing named assignment. An attempt with `taskMode: full-goal` must explicitly authorize full current goal dispatch, rather than infer it from a missing mutable map. Preserve changed-goal invalidation and sticky inheritance (`protocol/run-view.ts:280`, `core/project-run-attempts.ts:532`). Reuse successful worker evidence only for the authorized current task/goal; do not hydrate all prior agents to choose it.

Migrate the actual producer of the minimal known-failure/completed outcome needed by these commands, or keep the SQL task proof explicitly incomplete until that producer exists. Do not add a test-only accepted/failed execution constructor. Keep File as the one production authority and one budget ledger until the wider effect/accounting cutover.

Required regression proofs: actual initial plan -> worker known failure -> persisted request -> accepted task revision -> fresh released worker; identical original criteria/result and input subset; successful sibling retained; changed goal and reverted old goal cannot resurrect an old compact task; racing request/save, late predecessor response, cancellation and canonical replay reject/replay correctly; caught physical File/SQL failure rolls back head/revision/outcome/events/receipt; named current reads have constant query/returned-row shape behind genuine older revisions. Crash recovery and unknown effects require the following session/effect journal and must remain explicitly unclaimed.
