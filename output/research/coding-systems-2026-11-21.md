# Existing coding-agent approaches and implications for Buro

Checked 21 November 2026 against eight primary pages. This is an architecture comparison, not a matched performance ranking. Vendor engineering reports, historical editing benchmarks and real-repository benchmarks answer different questions.

## Findings by approach

| Approach / verified primary source | What is established | Cost or context limitation | What Buro should reuse or avoid |
| --- | --- | --- | --- |
| Simple composable workflows: [Anthropic, Building effective agents](https://www.anthropic.com/research/building-effective-agents), published 19 December 2024, modified 9 October 2026 | Describes routing, orchestrator/workers and evaluator/optimizer as distinct patterns. Recommends adding complexity only when evaluation justifies it. Coding is an example of tasks with dynamically discovered subtasks. | These are engineering patterns, not proof that one fixed team improves a 4B model. The current page explicitly directs readers to newer Managed Agents architecture. | Keep core control flow and its evaluation understandable. Select collaboration based on the problem; do not make every goal pay for every role. This can retain a mandatory independent verification policy. |
| Parallel research: [Anthropic, multi-agent Research system](https://www.anthropic.com/research/multi-agent-research-system), 13 June 2025 | A strong lead with specialized parallel investigators is deployed for broad information gathering. Detailed objectives, boundaries and output contracts prevent duplicate work. | The reported 90.2% improvement is on an internal research evaluation, with Opus 4 leading Sonnet 4 workers against single Opus 4. The 15× token statement compares multi-agent use with chat, not with the single coding agent. The article explicitly flags shared-context/dependency-heavy coding as a weaker fit. | Read-only code discovery can use parallel workers. Those research figures cannot justify five coding agents, equal-cost quality gains, or an autonomous Qwen 4B coordinator. |
| Single writer plus independent intelligence: [Cognition, Multi-Agents: What's Actually Working](https://cognition.com/blog/multi-agents-working), 22 April 2026 | Updates the older argument against multi-agents. Describes code/review iteration with clean reviewer context, optional stronger-model consultation, and managers coordinating scoped child tasks. Its preferred practical patterns keep write decisions single-threaded. | These are production observations, not a public matched-budget Qwen study. A weaker primary in the described SWE-1.5/strong-adviser experiment still failed to know when to escalate and what to ask; cheaper execution did not remove that quality ceiling. | Buro's clean reviewer and one-writer boundary fit this direction. Escalation should also use service-observed failure/no-progress signals, rather than rely entirely on a weak model recognizing its own limits. |
| Large hierarchical coding: [Cursor, Towards self-driving codebases](https://cursor.com/blog/self-driving-codebases), current 2026 follow-up | The final described system has a root planner, recursively scoped subplanners, isolated workers and feedback to the owner. Intermediate designs overloaded one executor with many responsibilities and became pathological. | This is a large-machine throughput experiment. It deliberately tolerates temporary errors and eventual reconciliation; its browser was a research project, not an externally usable quality-certified product. | Reuse explicit ownership, isolated workspaces and upward handoffs. Avoid a global integration bottleneck. Do not import its relaxed commit correctness or hundreds-of-agents assumptions into a 12 GB GPU product that promises accepted code. |
| Reasoner plus editor: [Aider, Separating code reasoning and editing](https://aider.chat/2024/09/26/architect.html), 26 September 2024 | Splits solution reasoning from formatting/applying file edits. Its historical editing benchmark includes same-model gains: GPT-4o-mini pair 60.2% versus 55.6% solo, and GPT-4o pair 75.2% versus 71.4% solo. | The pairs use additional inference, and some configurations are explicitly slow. These are historical model/editing results, not equal-token real-repository Qwen 4B evidence. | A focused small editor receiving a concrete solution is a stronger initial hypothesis than a small model inventing roles, discovering the repo and solving the whole problem simultaneously. Measure the second inference's value under Buro's global budget. |
| Local model integration: [Aider Ollama documentation](https://aider.chat/docs/llms/ollama.html), current page | Supports Ollama and explicit context settings; stresses that input/context handling is important for coding. | Parts of its default-context discussion refer to earlier Ollama behavior. Integration support is not proof of reliable editing by every local model. | Keep explicit `num_ctx`, actual model/digest metadata and conservative complete-input handling. Test model-specific edit formats independently from orchestration. Do not adopt old defaults as current universal facts. |
| Reusable coding runtime: [OpenHands Software Agent SDK](https://docs.openhands.dev/sdk), current documentation | Offers Python/REST APIs, coding tools, remote Agent Server, Docker execution, context compression and model-agnostic integration. The page states MIT licensing. | It is an available implementation substrate; the overview's benchmark claims do not establish superiority to Buro on identical tasks/models/budgets. Its action and runtime boundaries differ from Buro's scoped broker. | Evaluate it behind a runtime adapter before rebuilding equivalent machinery. Buro must retain or explicitly renegotiate workspace permissions, durable accounting, cancellation, effect observability and independent acceptance. Hidden backend requests must not be represented as fully metered. |
| Minimal baseline: [mini-SWE-agent v2](https://mini-swe-agent.com/latest/), current documentation | Uses a small agent core, a linear history, bash-only actions and independent subprocess execution. The same project provides model, environment and evaluation components. | The advertised small core excludes those supporting modules and Buro's product responsibilities. Its reported benchmark performance depends on the model and evaluation settings; the overview does not provide a matched small-local-model result. | Use a minimal executor as a baseline or optional backend. It tests whether Buro's context/tool/role additions improve outcomes. Do not infer that arbitrary bash or a tiny loop automatically replaces Buro's persistence, authorization and acceptance contracts. |

## Corrections to tempting interpretations

Cursor's intermediate removal of a separate planner was not its final recommendation. That iteration overloaded the executor; the final hierarchy restored narrowly owned planning. The article is evidence for empirical iteration and ownership, not a universal instruction either to remove or to require a coordinator.

Cognition's 2025 title should not be used as a current blanket rejection of teams. Its 2026 follow-up supports a writer augmented by reviewers/advisers. It also makes the weak-primary escalation problem explicit. Copying an agent organization chart alone is unlikely to close a large capability gap.

Context policy should depend on the role. A reviewer can avoid the author's accumulated reasoning while seeing the code and relevant task contract. An adviser resolving a context-sensitive decision may instead need a rich trace or explicit missing-context request. Neither copying every transcript to every agent nor always replacing history with a short summary is a general solution. This paragraph is an architectural inference from the sources, not a controlled result.

## Recommended Buro direction

The evidence supports reconsidering the policy layer before replacing the core architecture. Keep the service as the authority for budgets, allowed effects, files, test execution and acceptance. Let model-driven roles propose bounded tasks, edits, probes and findings through that authority. One mutable candidate and independent verification provide a coherent starting point on a single GPU; multiple roles can run sequentially.

Use three separately measurable strategies: a minimal executor with deterministic feedback; that executor with a fresh reviewer/repair loop; and the additional coordinator/test-author workflow. Add a reasoner-to-small-editor variant when model choice is allowed. The current same-model experiment is useful for isolating workflow value, but it should be repeated over multiple real tasks and successful baselines before claiming that local-model teams match frontier coding.

Treat OpenHands, Aider and mini-SWE-agent as possible execution adapters or comparison controls. Start by checking whether their isolation, event/trajectory and cancellation APIs can meet Buro's contracts. Importing an external backend must not silently expand tool authority or erase budget coverage limits. A wholesale framework migration has no demonstrated benefit from these sources alone.

Prioritize concrete context and progress: versioned source views, complete assignment contracts, service-derived failure evidence, unique findings and visible state changes. Preserve a bounded repair budget; escalation or task restructuring should follow repeated service-observed failures. A reviewer with no reproduced defect should not generate arbitrary extra work just to maintain a role cycle.

Measure the accepted final code and regressions, not agent count or commits. Report model/settings, global observed/reserved tokens, wall time, tool actions, no-progress loops, checks, review repairs and rejected outcomes. Equalize budgets and include direct/minimal baselines. The sources establish useful design hypotheses; Buro's own controlled results still determine which ones are worthwhile on its hardware and tasks.

No private project source, credentials, local inference or RTX endpoint was accessed for this research.

User policy clarification after this research pass: ordinary Buro goals should have no aggregate hard quota by default; hard request/token/time/session limits should be optional user settings. Retaining durable usage/effect accounting does not mean retaining mandatory default resource ceilings.
