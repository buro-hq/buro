## Boundary assessment

`ctx.projectContributions` owns separate startup-sealed catalogs for context format loading, project analysis and check recipes. Callbacks are captured trusted code. Core services receive resolved ports and continue to own durable admission, sessions, cancellation, receipts and settings application; no callback becomes an executor or project-store authority.

Context loaders receive a name and fresh copied bytes, never an original source path, resolver, model or filesystem port. Host adapters retain content-addressed originals, validate loader output, save loader provenance and verify hashes before analysis reads. The document adapter creates private temporary extraction input from those bytes; extraction failure is explicitly reference-only. The text-only model contract is unchanged: no vision capability or image payload is invented.

Research captures the resource profile before awaiting the first HEAD read, then captures the selected material descriptors in the same transaction as its durable command receipt. These are deliberate distinct admission moments, not a claim that every project byte was observed simultaneously. The record requires analysis identity, resource profile and materials; supported store transitions preserve them. The router selects and validates the admitted resource rather than rereading a mutable machine default. Managed start/resume derives material exceptions from the admitted research copy; when the old research record has been replaced, reopening its private session preserves its saved grant instead of expanding to the current material library.

An analyzer receives validated project/profile facts, source identity and authorized material representations. Its request and parsed result cross bounded typed contracts. Returned checks, components and commands remain suggestions. Applying them still goes through the existing source/profile revision checks and user-driven configuration operation. Read-only model research does not provide a final immutable acceptance view or an independently verified check result.

Recipe callbacks receive only their declared captured facts, not the complete project capture map, raw filesystem or shell. The host constructs provenance from observed HEAD, exact declared paths/presence and SHA-256 byte hashes; a recipe cannot append its own source-evidence field. Output schemas do not execute command strings. Actual setup/check execution remains with the existing prepared executor and check services after configuration, and final coding acceptance still requires its established checks/reviewer/effect authority.

## Simplicity and remaining limits

The three small typed catalogs correspond to different operations with different inputs and authority. Sharing the Cordis composition/sealing hook is useful; forcing them into one untyped universal plugin engine would obscure their contracts. The existing material storage, runtime routing, project profile and check execution paths are reused rather than introducing parallel journals or a discovery executor. The built-in Node recipe's removal from the filesystem repository manager is a concrete reduction in coupling.

Installed code remains trusted in-process code. Copying/frozen callback inputs and typed proposals are application boundaries, not isolation of malicious plugins or proof that an author never changes hidden closure state. Saved provenance is enforced through supported storage operations, not cryptographic tamper evidence against replacing an entire private state file outside the service.

Discovery may observe dirty working-tree manifests with their actual hashes and warnings; it is not a full immutable repository snapshot. Research reads and verifies its selected material copies, while its read-only source inspection remains proposal-oriented. Reference-only documents/images do not silently become model content. Existing import/read/proposal bounds and execution budgets remain present; this stage does not remove them.

Workflow/template contributions, an empty connected configuration/team bootstrap, independent package consumption, SQLite authority, default-none budgets, operational unknown-outcome preparation receipts and concurrent-goal scheduling are not completed by 4C2. No new blocking finding remained in the reviewed scope.
