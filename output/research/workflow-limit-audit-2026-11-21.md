# Аудит ограничений workflow, UI, CLI и хранения

Дата: 2026-11-21. Статический аудит текущих исходников; production-код не изменялся, модели и внешние проекты не запускались. Машинный реестр: `workflow-limit-inventory-2026-11-21.json`, 37 групп ограничений. Ограничения внутри model runtime исследуются отдельно; здесь проверены потребители политик и ограничения вокруг исполнения.

## Вывод

Удаление общего бюджета само по себе не сделает выполнение свободным от искусственных остановок. Сейчас цель дополнительно ограничивают два участника плана, две попытки планирования, максимум два исправления, одно автоматическое уточнение задания и фиксированные размеры входных конвертов. Эти ограничения живут в разных слоях. Обязательные поля схем и значения UI восстановят старое поведение, если изменить только бюджетный ledger.

Оптимальное направление: неограниченное по умолчанию число логических шагов и циклов улучшения, явные необязательные пользовательские квоты, ограниченная одновременность исполнения и проверяемый прогресс. При этом оставить независимую проверку результата, рамки доступа, ограничение одного пишущего процесса на общий worktree, контроль зависших инструментов и сверку действий с неизвестным исходом. Ограничение размера одного сообщения следует решать ссылками, порциями и адресным чтением, а не прекращением всей цели.

## Что мешает этому уже сейчас

### Команда и циклы работы

`maxWorkers` означает максимальное **общее число участников плана**, а не активных работников. Профиль принимает только 1–2 (`protocol/projects.ts:32`), план содержит не больше двух участников (`protocol/execution.ts:31`), UI предлагает 1/2 и подписывает поле как Concurrent workers (`src/components/organisms/ProjectProfileForm.tsx:216`). Исполнение ролей последовательное (`core/worker-assignments.ts:48`). Здесь нет внешней настройки «8» при скрытом фактическом максимуме «2»: ограничение согласовано, но его смысл и название неверны.

Нужно разделить длину рабочего процесса, число одновременно работающих независимых задач и емкость inference endpoint. Для общего worktree последовательный writer полезен. Ограничивать из-за этого общее число задач двумя не нужно. Независимый reviewer должен сохранить свежую сессию и проверяемое решение; исправления возвращаются writer с конкретными замечаниями.

`maxRepairs` обязателен, принимает 0–2, по умолчанию 2 (`protocol/projects.ts:33`, `adapters/files/project-manager.ts:213`, цикл `core/execution.ts:1240`). **0 уже означает отсутствие исправлений**, его нельзя переиспользовать как unlimited. Планирование ограничено двумя попытками (`core/execution.ts:924`); единственное автоматическое уточнение задания фиксируется в `run.workerReplan` (`core/worker-recovery.ts:7–10`, `core/execution.ts:1143`). Отдельно план требует 2–12 шагов (`protocol/execution.ts:7`).

Для следующей версии политики нужны отсутствующая квота = пользователь не задавал потолок; явное число = пользовательское ограничение. Настройки UI, CLI, схемы, сохранение, старые профили, возобновление запуска и сборка prompt должны понимать один смысл. Автоматические попытки должны зависеть от наблюдаемого изменения состояния и причин отказа. Повтор одинакового невалидного решения — повод изменить стратегию, уточнить задачу или запросить помощь; количество повторов не является доказательством прогресса.

### Время: четыре разных понятия

Текущий `DEFAULT_IDLE_TIMEOUT_MS` равен **10 минутам**, а не 20 (`protocol/domain.ts:61`). Start и resume записывают это значение заново (`core/execution.ts:322,445`). UI показывает остановку после такого простоя. Это таймаут здоровья сессии, а не общий дедлайн цели.

`ProjectProfile.turnTimeoutMs` принимает 10 секунд–15 минут и по умолчанию равен 360000 мс (`protocol/projects.ts:34`, `project-manager.ts:214`). Однако текущие completed-turn вызовы получают `run.timePolicy.idleTimeoutMs` (`core/execution.ts:913,974`). Поле профиля вводит в заблуждение: его сохранение не управляет этими вызовами. Следует удалить устаревшую настройку с миграцией либо связать её с однозначной политикой; простая смена default не исправляет расхождение.

Команда проверки имеет отдельный таймаут 1 секунда–15 минут; обнаруженные проверки получают 3 минуты (`protocol/projects.ts:8`, `project-manager.ts:198`). В форме нет настройки этого значения, а сохранение setup пересоздает команды с 5 минутами (`ProjectProfileForm.tsx:43`). Эти таймауты следует показывать и сохранять отдельно от квоты всей цели. Legacy `NodeChecks` посылает SIGTERM через 30 секунд без гарантированного последующего SIGKILL/reap (`adapters/checks/node-checks.ts:37`); это отдельный fallback-путь, не основной executor с профилем.

Наконец, клиентские 15 секунд ожидания ответа по умолчанию **не отменяют серверное действие** (`clients/socket-client.ts:167`). У verify, probe, models, import, apply другие интервалы. После таймаута pending request удаляется, поэтому новая команда пользователя может дублировать еще выполняющийся эффект. Для долгих действий нужны receipt/job ID, статус и сверка исхода перед повтором. UI connect timeout также не должен переводить цель в failed.

### Размер контекста и потеря доказательств

Планирование ограничено 24000 UTF-8 байт (`core/planning-policy.ts:7,135`), рабочий конверт — 128 KiB (`core/worker-envelope.ts:11,196`). Это реальные остановки независимо от общего бюджета. Для больших проектов нужны индекс, ссылки на материалы и дозагрузка релевантных разделов. Критерии приемки и authority нельзя молча обрезать ради прохождения лимита конверта.

Критическая несогласованность: исполнитель проверки хранит только **последние 30000 символов stdout/stderr** (`adapters/checks/project-commands.ts:66`), но `core/agent-context.ts:3` и marker в `worker-envelope.ts:14` обещают сохраненный полный лог. Ранние ошибки могут быть уже утрачены, и агент не сможет открыть обещанный источник. Краткий excerpt в prompt полезен; необходимо отдельно потоково сохранять полный лог в artifact и давать адресное чтение с offsets. Существующие 6K/2KiB excerpts и краткие planning summaries тогда становятся форматом представления, а не потерей исходных доказательств.

Большие легитимные правки также могут остановиться на чтении diff: Git before-blob ограничен буфером 2 MiB, измененный after-file — 1 MiB (`adapters/files/git-workspaces.ts:343–356`). Требуется потоковое чтение и постраничное представление, сохраняя полную проверку изменений. Похожие технические потолки есть у Git stdout (32 MiB) и fingerprint environment inputs (32 MiB/10000 файлов); поднимать числа без смены стратегии недостаточно.

### Материалы и долговременное хранение

Импорт имеет 8 MiB/file, 48 MiB/batch, 64 файла и глубину 12 (`adapters/files/context-materials.ts:10,154,180`). Библиотека ограничена 64 активными материалами проекта и **1000 записями всего, включая неактивные** (`context-materials.ts:263–272`). Удаление только ставит `active=false` (`:281`), поэтому повторные загрузки постепенно заполняют библиотеку. Цель может ссылаться на 32 материала; все активные project materials входят в ее контекст (`core/context.ts:10–16`). Суммарный контекст способен упереться в planning/envelope раньше этих счетчиков.

Нужны versioned library, фильтрация и ссылки по области действия, выборка релевантных фрагментов и страничное чтение. Ограничения кадра или объема одной порции можно сохранить, но они не должны превращаться в потолок объема всего проекта. Для больших файлов нужен chunked/streamed import. Входящий WebSocket кадр ограничен 12 MiB (`daemon/websocket.ts:32`); это не ограничивает исходящие snapshots/replay. Текущее файловое хранилище грузит полный документ и историю, подписка воспроизводит историю целиком (`project-store.ts:213`, `event-log.ts:49`). GC в основном пересохраняет документ и удаляет старые временные state-файлы (`project-store.ts:248`), а не создает масштабируемый архив. «Без квоты» требует bounded-memory read models, пагинации истории и отдельного artifact store.

## Что сохранить и переименовать

- `PROJECT_BUSY` сейчас означает один нетерминальный запуск на проект; настройки, research, verify/apply тоже имеют отдельные busy guards. Это защита общей mutable authority. Для параллельных целей нужны очередь и изолированные worktrees, а не удаление guard.
- `checkConcurrency` 1–4 ограничивает одновременную нагрузку, не число проверок за жизнь цели. Сохранить как отдельную resource capacity, автоматический выбор возможен.
- Разрешенные/защищенные пути, непересекающееся владение, registered checks, свежий reviewer, frozen/CAS evidence и сверка неизвестных эффектов не являются пользовательскими бюджетами. Их сохранять при любой квотной политике.
- Запрет Docker при `privateDataIsolation=true` (`executors.ts:55`) — capability boundary. UI должен объяснять совместимость выбранного исполнителя, а не предлагать небезопасный host fallback.
- Лимиты формы цели, роли и одного task envelope — ограничения команды/сообщения. Если сущность крупнее, использовать версионированные документы и ссылки; не просто убирать все `.max()`.

## Приоритет внедрения и проверок

1. Общая версия политики: default без пользовательских совокупных квот; явные opt-in числа, отсутствие новых defaults в UI/CLI; чистый переход без совместимости старых runtime/checkpoints; старые данные остаются архивом, новые запуски сохраняют свою исходную авторизацию.
2. Workflow: убрать общий потолок двух ролей/12 шагов, разделить capacity и число задач; заменить фиксированные repair/replan counts политикой наблюдаемого прогресса. Проверить больше двух последовательных заданий при одном writer и полном независимом review.
3. Доказательства: полный check log как artifact, адресные excerpts, корректная работа с большими diff/материалами. Тест: ошибка в начале длинного лога доступна reviewer; файл больше 1 MiB не исчезает из проверки.
4. Здоровье и продолжение: однозначные idle/tool deadlines, гарантированное завершение subprocess, клиентские job receipts и сверка timeout без дублирования эффекта.
5. Масштаб: пагинация библиотеки/истории и bounded-memory snapshots. Тестировать много исторических материалов и запусков; отсутствие пользовательской квоты не должно означать неограниченное потребление памяти одним запросом.

Реестр содержит конкретные условия, область остановки, рекомендуемое действие и проверки для каждой группы. Это результаты статического чтения: производительность и фактическое восстановление после остановок здесь не измерялись.
