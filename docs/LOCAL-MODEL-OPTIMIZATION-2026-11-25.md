# Local coding models and inference optimization

Checked against primary sources on November 25, 2026. Target: RTX 3060 12 GB, 32 GB system RAM, Windows, one local inference request at a time. Thinking and native tool calls are required for the Buro comparison.

## Recommendation

Keep Qwen3.6-35B-A3B as the measured local baseline. Take Gemma 4 12B into the next repository-quality comparison. The installed Q4_K_M package is 8.02 GB including its native assistant; its short 8K-context probes measured 61–82 decoded tokens/s with thinking and a working native tool round trip. This is speed evidence, not a completed Buro coding evaluation. Gemma 4 26B-A4B is a second experiment if the 12B model loses too much quality. Its 18 GB Ollama package requires partial CPU/RAM placement on this GPU. Google documents thinking and function calling for Gemma 4; Ollama marks the family as supporting both. No application-side text-to-tool fallback is needed. Verify the deployed tag's capabilities and an actual multi-turn tool round trip before including it in a coding run. Sources: [Ollama 12B package](https://ollama.com/library/gemma4:12b), [Google deployment guide](https://gemma.ai/deployment/ollama/), [Google function calling](https://gemma.ai/get-started/capabilities/function-calling/), [Google thinking](https://gemma.ai/get-started/capabilities/thinking/).

Qwen3.8-27B is a real open-weight release, with substantially stronger published coding results. It is a **dense** 27B model, so its per-token CPU offload cost cannot be inferred from our 35B MoE result. Four-bit weights alone have a theoretical lower bound of 13.5 GB decimal before metadata, mixed precision, buffers and context. It deserves a quality experiment, but has not demonstrated our minimum useful speed of 15 tokens/s. A Qwen3.8-Max API announcement is not evidence for a local 35B-A3B release. Source: [official Qwen3.8-27B card](https://huggingface.co/Qwen/Qwen3.8-27B).

## Qwen3.8-specific options

The new small-task Qwen run also exposed a reliability issue worth measuring across engines: Ollama 0.40.16 rejected one native tool call with `XML syntax error on line 3: unexpected EOF`. The corresponding HTTP stream had already started with status 200. The Windows engine log confirms a native parsing failure, but does not establish whether generation produced a malformed call or the parser mishandled it. Other native calls worked. This is a reason to compare native tool handling in llama.cpp, not to add an application parser for unsupported output. The task's behavior/tests/build passed; lint found 28 style violations, and the missing reviewer report meant the automatic correction cycle did not finish. [Ongoing task comparison](reports/preference-review-comparison-2026-11-25.html).

Ready-made optimized quantizations exist. The [Unsloth GGUF repository](https://huggingface.co/unsloth/Qwen3.8-27B-GGUF) lists approximately 16.6 GB for UD-Q4_K_M, 13.1 GB for UD-Q3_K_XL and 10.9 GB for UD-IQ3_XXS. These are different quantizations of the same dense target, not new smaller architectures with the full model's published scores. A 13.1 GB file still does not fit entirely into 12 GB VRAM after buffers and context. Two-bit variants are available, but are not the first quality-focused recommendation.

Unsloth's [November 11 Dynamic v3.1 update](https://unsloth.ai/docs/models/qwen3.8) claims improved accuracy at comparable quantized sizes and describes its agent/general benchmark conditions. This is the quantizer publisher's evaluation, not an independent guarantee of a 5–10% improvement in Buro. Its guide notes that the three-bit variants were not all regenerated because the measured benefit did not justify replacing them. Pin the actual file revision, not just the word “latest.”

Start with a pinned llama.cpp CUDA build and UD-Q4_K_M as the quality baseline. Then compare UD-Q3_K_XL if dense CPU offload is too slow. Test native MTP separately: Unsloth recommends another 1–2 GB of memory headroom, which may increase offload and negate the decode gain on our card. MoE expert-placement flags do not make this dense model sparse. The [Qwen card](https://huggingface.co/Qwen/Qwen3.8-27B) confirms built-in MTP training; actual speed depends on the inference implementation and draft acceptance.

[DFlash2 for Qwen3.8-27B](https://huggingface.co/z-lab/Qwen3.8-27B-DFlash2) is an auxiliary speculative drafter, not a standalone replacement model. Its published speed comparison uses an H200, SGLang, FlashAttention 3, xhigh reasoning and seven proposed draft tokens per verification. Those numbers do not predict an RTX 3060 result. The community [Ollama tag author's instructions](https://ollama.com/smtek/Qwen3.8-27B:Q4_K_M) explicitly distinguish clean baseline tags from custom map-k4v/DFlash2 routes that stock Ollama does not forward. A promising tag label is not proof that an accelerator is active.

The NVFP4 speedups in Unsloth's guide require Blackwell GPUs; they are not an RTX 3060 optimization. ExLlamaV3 is another possible engine, but its [current README](https://github.com/turboderp-org/exllamav3) requires CUDA build prerequisites and Triton on Windows and describes CPU offload for large MoE models. A compatible architecture and a fast all-GPU benchmark do not establish an efficient dense 27B hybrid deployment. Keep it secondary until this exact configuration is demonstrated.

The RTX disk had 43,068,764,160 free bytes (about 40.1 GiB) when checked on November 25. One Q4 artifact fits on disk; that is separate from inference memory. Model loading and engine changes remain scheduled after the original local runs. Qwen3.8 artifact downloading was later moved alongside the long-running Qwen medium case; its overlapping timing is explicitly labeled in the report.

During the November 26 storage cleanup, the unused local DeepSeek R1 14B and 32B packages were removed through Ollama, including their duplicate tag names. Unique stored bytes decreased by approximately 28.84 GB; duplicate names had shared weights and were not counted twice. Qwen 9B, Qwen 35B and Flint were retained. This reclaimed disk space, not inference RAM or VRAM.

## Optimization order

### Measured native preflights on this RTX

The November 26 Qwen native llama.cpp tests used build b12359 CUDA 12.4, automatic memory fitting, 8K context, Flash Attention, q8 KV and one slot. These are short diagnostic requests with thinking enabled, not full Buro coding tasks. The pinned Q4 and Q3 weights and the MTP head passed SHA-256 verification on the RTX host.

| ---------------------------------------------- | ---------------------- | -------------------- | ---------------------- |
| Qwen3.8-27B UD-Q4_K_M                          | 4.54 tokens/s          | 4.51 tokens/s        | Passed                 |
| Same Q4 plus Q4_0 MTP head, three draft tokens | 7.90 tokens/s          | 7.24 tokens/s        | Passed                 |
| Qwen3.8-27B UD-Q3_K_XL                         | 9.01 tokens/s          | 8.89 tokens/s        | Passed                 |
| Same Q3 plus Q4_0 MTP head, three draft tokens | 6.82 tokens/s          | 5.91 tokens/s        | Passed                 |
| Gemma 4 12B Q4_K_M, Ollama native MTP          | 71.23 tokens/s         | 61.37 tokens/s       | Passed                 |

MTP improved Q4 repeated-prompt decoding by about 1.7 times, but neither Q4 configuration reached the user's 15 tokens/s threshold. Both identified the fixture's zero-division bug after reading it through a native tool. This does not establish broader coding quality or architecture compliance. Q3 measured 8.9–9.2 tokens/s and also completed the tool fixture, without reaching 15 tokens/s. Q3+MTP completed at 5.9–7.8 tokens/s and was slower than Q3 alone in these requests. All four Qwen variants completed native tool round trips, but none met the speed floor; see the [live comparison snapshot](reports/preference-review-comparison-2026-11-25.html).

Gemma used Ollama 0.40.16 with its package-default `draft_num_predict 3`. The native log confirms `draft-mtp`, an 11.91B target and a 422.86M assistant. Target and assistant CUDA model buffers were approximately 7024 and 429 MiB, excluding KV and other buffers. Ollama /api/ps reported only about 1.45 GB, inconsistent with those buffers, so that field is not used as total VRAM evidence. The warm request took 3.81 seconds overall; its first request took 31.71 seconds including 22.36 seconds of model loading. Qwen cold probes began after server loading, so their cold wall times are not equivalent. Prompts and engines also differ between families: this is a deployment preflight rather than a controlled model leaderboard.

Ollama documents Flash Attention, q8_0/q4_0 KV types, loading lifetime and parallelism in its [FAQ](https://docs.ollama.com/faq). llama.cpp documents prompt caching, cache reuse, context checkpoints, batch/ubatch, MoE placement and speculative modes in its [server documentation](https://github.com/ggml-org/llama.cpp/tree/master/tools/server). Availability in current upstream documentation does not establish support in the installed Windows binary. Qwen's [35B card](https://huggingface.co/Qwen/Qwen3.6-35B-A3B) recommends temperature 0.6/top_p 0.95/presence penalty 0 for precise coding in thinking mode; these already match the exposed settings of our comparison. Top-k and other defaults still depend on the deployed engine.

Preserved reasoning can help Qwen's agent consistency and cache use, according to its card. Buro's Ollama provider already forwards private continuation `thinking`; adding duplicate reasoning into public history is not a justified fix. Gemma has its own history rules, including retaining thinking across tool turns but excluding it from ordinary earlier turns. Follow the native engine/template behavior rather than imposing one model's rule on all adapters. [Qwen guidance](https://huggingface.co/Qwen/Qwen3.6-35B-A3B#preserved-thinking), [Gemma history guidance](https://huggingface.co/google/gemma-4-12B).

No engine settings or model loading were changed during the original matrix. A later Qwen3.8 artifact download overlapped the Qwen medium case, so its affected wall time is not an isolated speed measurement. The completed native probes pin the Qwen files and engine build and record the installed Gemma digest. The next experiment should run the same small/medium repository-quality tasks on the viable candidate, using the intended 32K context and the repaired schema transport. Accept a faster configuration only when behavior and architecture remain sound.

One Buro-specific hypothesis also deserves measurement: `modules/sessions/context.ts` preserves the task and recent complete exchanges when a conversation outgrows its request allowance, replacing omitted content with a notice. As the retained suffix changes, the input prefix after that notice changes too. This can reduce prefix-cache reuse and remove earlier verification evidence from the model's current view. It does not prove the cause of the measured input time, but context stability and repeated work should be measured alongside engine kernels. A retained history is not automatically an efficient request context.

## Command-output reduction and RTK

The Gemma small-task trace contains a recursive grep through dependencies/binary files whose captured result reached the 256 KiB process-output cap, and a failing test result with 62,164 bytes of stdout/stderr. Both are significant input noise. Buro currently exposes captured command output as JSON and estimates request size at four characters per token. Several native requests reached almost the whole 32K context and stopped after very short output. Reducing command noise and improving context estimation are related but separate changes.

[RTK](https://github.com/rtk-ai/rtk) provides command-specific filters and raw-output recovery. On an exact replay of that captured Node test output, the installed 0.30.0 `rtk test` emitted 189 bytes but returned 0 for the child's exit 1. An isolated, SHA-256-verified [rtk-oss 1.2.1](https://github.com/rtk-ai/rtk/releases/tag/v1.2.1) returned the correct exit 1, but its generic test fallback still emitted only the final five lines plus a recall reference. Neither short result adequately described the multiple failures. This is a compatibility observation about these commands and this fixture, not a claim that every RTK filter loses errors. The global binary and Buro command execution were not replaced.

The first product change instead uses [Node's public test-reporter events](https://nodejs.org/docs/latest-v24.x/api/test.html#custom-reporters). `npm test` omits successful-test listings while retaining errors/stacks, diagnostics, stdout/stderr, skips and totals. `npm run test:verbose` retains the ordinary full listing. In the measured 132-test suite, both modes passed: compact output was 2,937 bytes versus 17,334 bytes verbose, about 83% fewer bytes. The integration fixture deliberately fails and verifies exit 1, nested failure details, skip reasons and captured diagnostics. This is output reduction, not an 83% wall-time or total-token improvement. The live Gemma benchmark remains on its original target and runtime.

For wider tool compression, keep process execution and its exit/error independent from any replaceable output filter. Preserve full captured evidence and offer range-based retrieval; expose summaries to the model once rather than repeatedly changing stored history. RTK's stdin filters can be an optional implementation for supported formats. Unknown formats should retain usable diagnostics rather than treating a tiny result as success. A size reduction alone is insufficient evidence of a safe filter. This broader Buro tool-result integration is still pending.
