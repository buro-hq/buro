# Evidence for same-model coding teams

Research date: 2026-11-21. Primary papers and official implementations only. This is a focused evidence review, not a systematic meta-analysis. No models, RTX host, credentials or user source projects were accessed. Only this research note was added.

## Assessment

The useful hypothesis for Buro is that separated responsibilities plus executable feedback can improve a model's result. The stronger claim that several conversations with the same small model inherently produce better repository changes is not established by the evidence found here.

No retrieved study directly establishes that a Qwen 4B/9B same-model coding team beats an equally funded single-agent coding harness on held-out real repository issues. There is positive function-level evidence, working simpler repository systems, and relevant but non-coding small-model studies. These should remain separate.

## Two particularly relevant cautions about criticism

AgentCoder's own ablation gives only a small improvement when another LLM supplies tests and the programmer reasons about them without execution. The much larger improvement appears when tests are actually executed and feed repair. Its generated-test accuracy against canonical solutions is still imperfect: GPT-3.5 test-designer results are 87.8% / 89.9% on HumanEval / MBPP; GPT-4 is 89.6% / 91.4%. Incorrect expected outcomes can steer a correct implementation into a wrong repair. These are paper-reported experimental figures, not guarantees.

MAST documents incorrect verification and premature termination among multi-agent failure modes. A fresh conversation and a reviewer title are useful isolation mechanisms; they do not independently establish truth. Requiring specific findings, source identity and executed evidence remains important.

Our declarative queue experiment deliberately makes the service compute expected results from a trusted reference. This cleanly measures proposed-input value and repair mechanics, but is easier than generating correct tests for arbitrary application behavior. It must not be advertised as a solved general test-authoring problem.

## Architecture implications — inference from the evidence

Keep Buro's durable owner state, workspace isolation, scoped tools, cumulative budgets and acceptance evidence. These are useful regardless of which agent strategy wins. There is no retrieved evidence that replacing the modular core with a conversational multi-agent framework alone would improve coding quality.

Make strategies interchangeable on top of that core: a focused executor; executor plus external checks and debugging; a fresh critic/repair loop; independent test proposal; candidate sampling and selection; or stronger coordination with smaller workers. Roles should produce a verifiable artifact or new evidence, not just another opinion. A controller should handle test execution and routing IDs; it need not ask a model to reproduce bookkeeping.

Prefer bounded shared artifacts—goal/constraints, current source identity, scoped changes, actual test receipts, unresolved findings—over forwarding full histories. New information or a changed patch should justify the next model call. Same-model agents have correlated capabilities; independence of context should not be equated with independence of errors.

## Evaluation needed before a product claim

- Preserve the three product modes, but add a compute-matched control: give the single executor comparable inference for self-debugging or multiple independently sampled patches and test-based selection. Equal maximum budgets alone do not isolate role structure when actual use is three calls versus twelve.
- Use paired real issues and multiple seeds/repetitions, plus small synthetic cases for diagnosis. Keep model, quantization, context, tools, disclosure and final hidden acceptance identical where possible.
- Track code correctness separately from workflow/review completion, regression rate, wrong-test rate, false approval, accepted changes per elapsed time and observed inference. Native internal call accounting may remain unknown.
- Attribute failure stages: invalid orchestration proposal, missing context, tool/interface error, no-progress implementation, incorrect generated oracle, stale evidence, reviewer miss or budget/deadline. Aggregate pass rate alone will conceal the improvement target.
- Record the test-time opportunity given to every baseline. Budget spent on planner/tester/critic is inference that could otherwise have bought another candidate or another grounded repair attempt.

The defensible current product hypothesis is an evidence-driven coding workflow that can use teams when they add measurable value. Reliable improvement of a small local model remains an experimental question.

User policy clarification after this research pass: ordinary Buro goals should have no aggregate hard quota by default; hard request/token/time/session limits should be optional user settings. Retaining durable usage/effect accounting does not mean retaining mandatory default resource ceilings.
