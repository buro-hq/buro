## Source boundary assessment

The filesystem store and application bootstrap now open new teams without implicit default or operational roles. Explicit fixture roles are confined to test/demo composition. Role templates contribute validated content and a revision, without model preferences, executor handles, capability grants or an alternative acceptance policy. Workflow selectors receive detached, frozen service-operation descriptions and return template IDs. The host supplies role identity, version, timestamp and provenance.

Execution, research and result preparation require a workflow-role resolver. An existing role is reused as authored rather than overwritten by a current template. New service roles are resolved inside the owning durable operation transaction; their event projection carries newly created roles so connected clients can update both the team and derived eligibility. Research additionally records its exact role snapshot and role-resource decision before runtime start. The router validates that captured selection rather than the mutable profile's coordinator slot. Role kind/title/template branding provides no additional capability.

Current user role edits append a user-authored version and retain available lineage. The public save command constructs provenance in the host rather than trusting a caller-supplied origin. Captured research inputs include the complete role snapshot and the authority part of its resource decision; the independent actual-storage mutation test confirms those cannot be rewritten through a supported transaction.

The new run captures its selected workflow identity before planning. Team materialization reads that saved identity, so resuming a pre-plan run after startup composition changes must not attribute new coordinator-created workers to today's unrelated workflow. This is provenance for content creation; backend admission, scope, effect journals, selected checks, immutable final verification and independent review remain separate service authorities.

Optional replacement catalogs are real startup composition: an explicitly supplied category suppresses that category's built-ins, while omitted categories keep first-party composition. Independently rerun tests prove replacement loader/tool implementations execute through their existing bounded ports, and the new custom-only workflow test proves selection is not only a catalog-listing feature. Catalog sealing and the architecture regression protect against late registration and replacing the resolver's caller-owned catalog options.

## Final history, routing and projection assessment

The final file role history is an immutable ordered prefix. New definitions must append the next version; duplicate keys, reordering, deletion, skipped versions or old content/provenance rewrites reject. A user's later edit creates a new version rather than invalidating an accepted older version.

The final captured-role guard compares complete retained role definitions, including provenance, and preserves the saved run workflow identity. A captured version still referenced by a service, worker-assignment or operation grant cannot disappear. An unreferenced current planning roster can be replaced during replanning. This intentionally does not promise that every superseded worker snapshot remains in the current run roster; the project role-version history and prior events preserve their own evidence. The independently rerun regression distinguishes referenced service-role removal from legitimate unreferenced replacement. Operational resource decisions retain their existing immutable authority tuple, with the global complete-role guard supplying provenance protection.

Created worker roles now enter `roleVersions` in the same transaction as the validated plan and are published in that event before worker dispatch. They remain available even when later implementation or acceptance fails; their existence means that the team defined a role, not that code was accepted. Existing names are rechecked before that write. Later user versions are future-facing while the current execution retains its captured version; unchanged checks/review/source verification continue to govern acceptance.

Historical research routes carry an immutable captured role, resource pool and decision in private route storage. Current team changes and a newer research record cannot retarget the older native session. The existing actual routed/private-session regression was rerun against the final implementation and preserved the original grants after the research record changed. Route storage rejects role-provenance or native-session replacement.

The UI owner corrected `resultAgents` parsing to retain its optional `AgentSession`, which previously disappeared during Zod parsing. The independently rerun session-view regression proves protocol round-trip preservation and display of the saved role version/provenance after the user has edited the current team. If the matching old definition is unavailable, the UI does not substitute today's unrelated role definition. This reviewer reran the protocol/model helper proof, not the owner's browser screenshots.

The final architecture negative test found a real route admission gap: matching admitted research could exist while a private route omitted both its saved role grant and role decision. The original condition checked only the presence of a decision, so both missing fields escaped that guard. The parent changed the condition to require the original grant when either matching admitted research or a saved research decision exists. This reviewer inspected the fix and independently reran the regression using actual `FileRuntimeRoutes`: a forged profile-default route cannot bypass an admitted user pin, and no backend resume occurs. The immutable grant remains available to legitimate older research routes after their public research record changes. No blocking finding remains in the reviewed scope. The parent owns the final full suite/build, including unrelated fixture migrations. Existing immutable checks, acceptance/reviewer, unknown-outcome recovery and historical-route tests remain authoritative.

## Simplicity and limits

On-demand materialization removes unconditional team seeding and the parallel operational-role list. One resolver and one typed provenance schema are useful shared seams. Existing store transactions, runtime routes and domain events provide the required atomicity; another role store, workflow execution engine or model-routing authority is unnecessary for this increment. Keep data/template selection separate from execution mechanics.

These workflow contributions currently select role templates for the existing service operations. They do not define an arbitrary workflow DAG, replace the coordinator loop or remove final checks/review. Coordinator-created implementation roles still come from the validated plan and receive host-authored provenance. Explicit startup replacement is not dynamic installation or a sandbox for malicious in-process code.

The proof establishes an empty initial team, not that all machine provider/model settings, checks or project profiles are empty by default. Broader independently consumed package distribution, SQLite authority, default-none execution budgets, operational unknown-effect receipts, concurrent-goal scheduling and a complete configurable workflow graph remain separate work. No final full-product architecture or live-model-quality claim is made here.
