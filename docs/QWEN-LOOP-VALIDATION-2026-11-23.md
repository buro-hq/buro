# Qwen 4B: контекст координатора и реальный цикл

Дата отчёта: 23 ноября 2026; этап начат 22 ноября. Исходный коммит `7daf785`. Пользователь разрешил повторные реальные прогоны на новых синтетических проектах, затем сравнение с RTX. Оригинальные проекты и `output/ux/` сохранены. Сокращённый scope беты и публикация не утверждены.

## Кто ограничивал контекст

Сравнительный стенд задавал Ollama окно 16 384 и output 2048. Buro использует консервативную верхнюю оценку по UTF-8 байтам, а не фактический tokenizer count. Поэтому `MODEL_CONTEXT_EXHAUSTED` в этих прогонах — отказ политики Buro до следующего запроса, а не сообщение Ollama о заполнении физического окна.

Установленная Mac-модель — `qwen3:4b-instruct-2507-q4_K_M`, digest `0edcdef34593eac1aa2be9c7d06c432dcf81945adca5eca2f27662c18f168ba0`. Модели не скачивались, настройки машины не менялись. Проверялся именно этот вариант 4B; установленный `qwen3:4b` с другим digest не подменяет результат.

## Что исправлено в общем механизме

Координатор использует тот же подключаемый механизм сегментов, что и worker. Между завершёнными сервисными действиями хост может атомарно сохранить переписку и приватное continuation в архив и начать окно с актуальным пакетом: полная цель, рабочий план, назначения и задачи, фактические результаты worker, checks/review, каталог ролей и действий. Старый ответ модели не становится полномочием или доказательством приёмки. Отклонённое предложение передаётся отдельно как недоверенный контекст для исправления.

Ротация учитывает как рабочий запрос, так и полную схему будущего формального ответа и его инструкцию. При необходимости завершённое закрытие шага архивируется перед отдельным окном формального ответа. История не удаляется; завершённые инструменты не исполняются повторно. Неопределённые операции, отмена, смена Git identity или запрещённые изменения блокируют переход. Неуспешная запись архива не меняет cache и не запускает новый inference.

Готовность координатора выбрать любое зарегистрированное действие завершает текущий шаг работы с репозиторием. Для этого не требуется завершить всю цель. Это исправляет общее зацикливание «дальше запросить review» → `continue` → повторное чтение. Порядок plan/delegate/check/review/finish не фиксирован, worker сохраняет свою семантику завершения. В prompt нет веток по имени или размеру модели. Полная цель находится в актуальном packet и не дублируется в system instructions.

Default segment policy v3 не ограничивает число окон; прежние четыре сегмента и отдельный File ceiling в 15 архивов удалены. Явно заданный `maxSegments` остаётся поддержанным ограничением. Это не завершает полный default-none: остальные request/tool/check-feedback бюджеты остаются, а File сохраняет историю целым растущим aggregate. Нужны incremental journals и paged active history; один слишком большой обязательный packet также не помещается в конечное окно автоматически.

## Сохранённые реальные прогоны

Все неуспехи сохранены отдельно; исправление кода и сервисная приёмка различаются.

| Прогон                                                                               | Результат                                                                                                                                                                                          |
| ------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `actions-qwen4b-baseline` — исходный командный case, 16K                             | Worker исправил оба файла, public 3/3 и holdout 5/5. Приёмки нет: история координатора превысила оценку контекста; 18 HTTP-генераций с diagnostics.                                                |
| `actions-qwen4b-context32k` — тот же case, явно выбранные 32K                        | Код прошёл public 3/3 и holdout 5/5. Координатор повторял review без сервисного check; стенд остановил 24-й лимит. Приёмки и отдельного worker нет. Увеличение окна не доказало исправления цикла. |
| `actions-qwen4b-segmented-repair16k` — repair fixture v1, первый вариант сегментации | До сервисного действия не дошёл: рабочая история поместилась, но большая финальная схема вызвала отказ контекста. Repair не покрыт.                                                                |
| `actions-qwen4b-final-repair16k` — repair fixture v2, до исправления смысла closing  | Окна менялись, но координатор повторял `continue` с предложением запросить review; остановлен лимитом стенда 24. Repair и приёмка не покрыты.                                                      |

| `actions-qwen4b-current-team16k` — после исправления смысла closing | Отдельный worker исправил код, public 3/3 и holdout 5/5. До review снова отказ контекста: в packet обнаружено повторное описание transport/session и worker result. Дубль удалён в последующем исправлении. |
| `actions-qwen4b-current-repair16k` — компактное состояние | Сформировано действие review без обязательного service check. После отклонения packet с полной схемой превышает консервативную оценку 16K; repair не покрыт. |
| `actions-qwen4b-current-repair32k` — явные 32K с разбиением | Координатор повторил преждевременный review. Полного цикла нет; последнее завершение `LIVE_OUTPUT_INCOMPLETE`, 24 HTTP-генерации с diagnostics. Это не успешная проверка reviewer/repair и не доказательство общей неспособности 4B писать код. |

`final` в имени промежуточного файла — историческое имя попытки, не заявление о завершении продукта. Их bytes и отдельный manifest не переписываются последующими попытками.

Исходный сравнительный case v1 сохраняет прежние fixture/task/oracle hashes и обязательного отдельного worker. Новый repair case v2 имеет свою идентичность: правильный `priority.mjs` защищён, изменяем только `queue.mjs`, исходник проходит public 3/3, но holdout 4/5 из-за неверного направления сортировки. Задача явно просит настоящее независимое review до правок. `repairCoverage` требует реального `changes_requested` исходного tree, другого исправленного tree, новых успешных checks, другой свежей reviewer-сессии с `approved`, exact accepted tree и полного public/holdout. Принятый кандидат без исходного отклонённого review не считается доказательством repair.

Стенд сохраняет отдельную проверку исходника до dispatch, независимо от production `Run.baseline`: новый action loop не обязан автоматически выполнять baseline. Проверки, fresh review и приёмка не ослаблялись. Pilot по-прежнему ограничен 24 HTTP-генерациями, 65 536 reserved output и пятью минутами; это явные ограничения эксперимента, не обещание безлимитного продукта. Контекст 32K был отдельным объявленным экспериментом; основные прогоны после исправлений остаются на 16K/2048.

## RTX и границы вывода

`192.168.50.10:11434/api/tags` несколько раз завершился timeout, включая повтор после исправлений. RTX inference, SSH, сканирования сети, скачивания модели и изменения конфигурации не выполнялись. Сравнение с `qwen3.5:9b-q4_K_M` остаётся невыполненным до доступности прежнего endpoint.

Это небольшие синтетические задачи, не оценка общей надёжности 4B и не рейтинг моделей. Прежние DeepSeek/Codex trials остаются историческими; этим этапом они не перепроверены. Crash recovery, чистая установка, полный default-none и сохранённый Run/journal план остаются отдельными незавершёнными требованиями.

## Проверки и следующий шаг

Полный suite **1442/1442**, без skips; build/typecheck и **17 UI-сценариев** прошли. После последней однострочной коррекции передачи optional `ToolResult.exitCode` независимо прошли **14/14 controller cases**; полный suite предшествует только этой коррекции metadata. Independent review подтвердил exact archives, полный worker result один раз в packet, сохранённые grants/receipts и metadata плагинов. [Validation receipt](../output/research/qwen-context-validation-2026-11-23.json) сохраняет границы проверок, исходные отчёты и hashes.

Практический вывод ограничен фактами: 4B несколько раз исправила исходный case с public/holdout 8/8; надёжное автономное завершение с проверками и reviewer не доказано. Увеличение окна само по себе не устранило ошибочные решения координатора. Новые реальные попытки в прежнем ограниченном режиме остановлены. По прямому указанию пользователя следующим этапом немедленно убираются стандартные lifetime budgets и проводится сквозной аудит прежних предположений, с сохранением usage и явно заданных ограничений. Этот этап ещё не объявляет их устранёнными.
